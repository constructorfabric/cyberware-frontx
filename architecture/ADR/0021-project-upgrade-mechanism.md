**ID**: `cpt-frontx-adr-project-upgrade-mechanism`

## Context and Problem Statement

The project-state contract keeps everything the CLI tracks about an applied template in one document, `.frontx/project.json`, keyed by template name: `templates[name] = { origin, version, targets[] }` (`cpt-frontx-adr-project-provenance-record`). A template name carries exactly one `origin` and one `version`, and `targets` is the list of paths that name has been applied to; there is no per-target `origin`/`version` field and no per-instance provenance record an upgrade could read as a baseline. An upgrade mechanism operating on one applied template *instance* at a time, diffing against a per-instance record written at apply time, therefore has neither a unit nor a baseline source to work from. What is the unit an upgrade operates on, where does its baseline come from, how does the content of that baseline actually move onto an already-applied target without destroying a developer's own edits or silently reconciling two changes to the same file, and how is that move undone afterward, when a single registry entry names every target a template has been applied to and holds no per-instance record of what was there before?

## Decision Drivers

* **One origin and one version per template name** — the registry structure itself (`templates[name] = { origin, version, targets[] }`) has no field for a per-target origin or version; any upgrade unit finer than "the template name" cannot be expressed without adding fields the project-state contract does not define (`cpt-frontx-adr-project-provenance-record`).
* **A minimal, algorithmic baseline for v1** — the baseline an upgrade diffs against must be derivable from data the project already keeps for other reasons (the registered `origin` and `version`), not from a dedicated per-instance provenance record or per-file content hashes maintained solely to serve upgrade.
* **Determinism over partial-success granularity** — a registry entry that names one `origin`/`version` for potentially several `targets` must never end up describing a template partially upgraded and partially not; the entry's truth (which version this name is at) must hold for every target it names at the end of the operation.
* **Reviewable, non-destructive, reversible, and delivered here** — a developer must be able to review an upgrade before it lands, an in-progress edit must never be silently destroyed, and an applied upgrade must be reversible; unlike the unit and the baseline, none of these three properties means anything until a file-level mechanism actually writes and later unwrites content, so the mechanism this decision fixes is what discharges them, not a placeholder that keeps them open for a later mechanism to satisfy.
* **A developer's own edit is never rewritten by algorithm** — where a file has changed independently on both sides, by the new template version and by the developer, no mechanism may guess at reconciling the two inside the file itself; a whole-file decision — write it, or refuse the whole upgrade and say why — is the only answer that cannot destroy an edit, so a textual, hunk-level, or region-marker merge is off the table regardless of how the changeset ends up represented.
* **Reversal costs no more state than the baseline already does** — if the forward move can work without a stored content snapshot, by re-deriving its baseline from the name's recorded origin, the same must hold in reverse: reversal is a property the recorded origin history can deliver on its own, not a reason to introduce a second stored artifact the forward direction had no need for.
* **Ownership subtraction still applies** — regardless of unit, an upgrade must not touch ground the applied template does not effectively own, as `cpt-frontx-adr-template-ownership-boundary-declaration` computes it, nor any nested target belonging to another template.
* **Deliberate re-application must stay distinct from accidental overwrite** — re-running `apply` against an unchanged, already-applied target must remain an idempotent no-op that protects an edited instance; intentionally moving a target onto a new template version is a separate, named operation (`upgrade`), never something `apply` does by itself.

## Considered Options

* **Per-applied-template-instance upgrade with a provenance-derived baseline and file-level reconstruction** — one engine invocation per target, diffing against a dedicated per-instance provenance record and reconstructing a three-way merge from that record's origin.
* **Per-target upgrade with independently versioned instances of the same template** — keep the instance as the unit, but let each target of a given template name carry its own `origin`/`version`, so `login` can sit on v2 while `registration` stays on v1.
* **Atomic all-targets upgrade with a `project.json`-read baseline, whole-file classification, and one-generation reversal** — the unit of upgrade is the template *name*; `frontx upgrade <templateName> <new-origin>` validates and updates every target listed under that name as one atomic operation, using the name's own `{ origin, version }` entry as the baseline, moving content onto each target through a three-way whole-file classification against that baseline, and reversing an applied upgrade by re-running the same classification against the one preceding `{ origin, version }` the commit that applied it recorded.
* **Textual three-way merge with conflict markers in the file** — classify nothing; instead merge the baseline, the candidate, and the on-disk content line by line, writing conflict markers into a target file wherever the merge cannot resolve automatically.
* **Whole-target re-materialisation from the new payload** — skip classification entirely and overwrite every file the new template version declares within a target's effective ownership, whether or not the developer has touched it.
* **A retained pre-upgrade content snapshot under `.frontx/` as the restore carrier** — capture a copy of every target's pre-upgrade content into the repository at the moment an upgrade commits, and read that copy back for both the forward diff's baseline and a later restore.
* **A per-file content-hash index maintained for upgrade** — maintain a persisted hash for every file inside an applied target's ownership, updated on every apply and upgrade, and use it to detect which files have changed instead of comparing content directly.

## Decision Outcome

Chosen option: **Atomic all-targets upgrade with a `project.json`-read baseline, whole-file classification, and one-generation reversal**, because it is the only option that fits the registry structure the project-state contract fixes (`cpt-frontx-adr-project-provenance-record`) while also moving content onto a target, and reversing that move, without inventing state the registry does not already carry: a three-way whole-file classification reads its baseline from the same `{ origin, version }` entry every other command already reads, needs no per-instance provenance record and no file-level reconstruction machinery the contract has no place for, and gives v1 a deterministic, dependency-free upgrade unit whose forward move and reversal are both derived from data the project keeps for other reasons.

`frontx upgrade <templateName> <new-origin>` treats every target listed under `templateName` in `.frontx/project.json` as one unit: it validates the new origin against all of that name's targets and, on success, updates `origin` and `version` for the name atomically — every target moves together, or none do. A partial upgrade of one target to a new version while a sibling target of the same name stays on the old version is not a supported state in v1; it is a direct consequence of the registry recording one `origin` and one `version` per name rather than per target. The baseline an upgrade diffs against, and the baseline a restore diffs against, is the name's own registry entry — `{ origin, version }` in `project.json`, or, for a restore, the one preceding `{ origin, version }` this decision has that same entry also carry — never a per-instance provenance record or a per-file hash set; no such record exists to read, and none is introduced.

`upgrade` is the only path permitted to change a template name's `origin` while its `targets` list is non-empty; when `targets` is empty, `register --replace` is sufficient because there is no applied ground to reconcile. Re-applying a since-changed template onto an existing target is, by definition, an `upgrade`, never a plain `apply`: `apply` against an already-applied, unchanged target remains an idempotent no-op, precisely so an edited instance is never silently clobbered by a template that moved on. An upgrade computes and applies its changes only within the effective ownership the whole six-term subtraction `cpt-frontx-adr-template-ownership-boundary-declaration` enumerates, applied whole and never as a subset, and computed once, from the candidate manifest alone — the version whose content is being placed, together with `projectOwnedRoots`, the target's own local origin folder, `.frontx`, and the environment-owned entries — never recomputed per path and never mixed with the baseline manifest's own declared exclusions; and, beyond that, never into a nested target belonging to another template. Protected and other-owned ground is therefore never disturbed, regardless of how many targets are being moved at once. Every outcome — success, `VERSION_MISMATCH`, or any other failure — is reported through the CLI's single JSON result envelope, consistent with every other command.

The two manifests in play — the one behind the recorded baseline and the one behind the candidate — can declare different `excludedSubtrees`, and using the candidate's alone has consequences a developer must be able to read from the plan. Ground the candidate manifest now excludes that the baseline manifest owned is left exactly as it sits on disk: never removed, never written, reported in the plan as `SKIPPED`. Ground the candidate newly claims because it dropped an exclusion the baseline held becomes ordinary eligible ground like any other: a developer's own file already sitting there is a doubly-changed file and refuses the whole upgrade with `CONTENT_CONFLICT`, and a nested target belonging to another template sitting there refuses with `TARGET_CONFLICT` — the same nesting-aware check a batch `apply` already runs, joining upgrade's refusals with no new code invented. Because a restore is this same engine with the preceding origin as its candidate, its boundary is computed from the preceding manifest, read from the other side of the identical computation: reversal is symmetric by construction, not by a rule written specially for it. That symmetry has a boundary of its own: a restore returns every target to the preceding origin's content only within the preceding manifest's boundary. A file the forward upgrade added into ground the candidate had newly claimed lies outside that boundary from the restore's point of view, so a restore leaves it exactly where it is, reported as `SKIPPED` rather than removed — a restore reproduces the pre-upgrade state within that boundary, not unconditionally.

The plan reports, alongside its operations, every payload path it did not act on because the boundary excludes it — for any of the reasons that boundary is computed from, as `SKIPPED`, never written. Those reasons are the five terms CLI-5's effective-ownership subtraction names (an `excludedSubtrees` entry, a `projectOwnedRoots` entry, the target's own local origin folder, `.frontx`, an environment-owned entry), plus one that is not an ownership term at all: another template's nested target, which the conflict checker's geometry excludes separately. The distinction is worth keeping because the count is cited across records: `cpt-frontx-adr-template-ownership-boundary-declaration` fixes effective ownership as the target minus those five and nothing else, and brings a nested target in only for the narrower question of what `delete` may remove. Folding it into the ownership terms here would give one named quantity two different memberships in two different records. This is the discoverability channel `cpt-frontx-adr-template-ownership-boundary-declaration` already relies on when it says a developer learns from the report that a file they did not realize was protected stayed on an older version; an upgrade's plan is where that channel now speaks for the upgrade path, and it speaks for every one of those exclusions, not only the part of the boundary that shifts between the baseline and the candidate manifests.

The changeset an upgrade computes is a per-target, per-file plan of typed whole-file operations, computed once for the whole name before anything is written and carried as the data payload of the same JSON result envelope every other command uses — `cpt-frontx-adr-cli-machine-readable-output` fixes the envelope's outer shape and code vocabulary but not any command's `data` payload fields, and `cpt-frontx-adr-contract-schema-ownership` puts that field layout in exactly one owning FEATURE, the same way it owns the project state document's. What this decision fixes is the shape class that payload must express: an origin-and-version pair naming where the transition starts and where it ends; every target the plan covers; for each target, the payload paths it skipped because they fall outside the candidate-manifest boundary (`SKIPPED`, above); and, for every remaining path, one operation named by one of five kinds — `ADD`, `REPLACE`, `REMOVE`, `KEEP_LOCAL`, or `UNCHANGED`. Granularity is the whole file: there is no hunk, region-marker, or line-level representation anywhere in this plan, because a plan a developer reviews before anything is written must be reviewable as a list of files and actions, not as textual deltas inside them.

Computing that plan is a three-way classification, never a merge, over every path at least one of the baseline or candidate payloads declares within the boundary above — never every path the boundary merely admits, so a developer's own file or symlink sitting there that neither payload ever declared is not examined at all. A payload is regular files only, compared by their actual bytes, and comparison is defined over absence explicitly: an absent path is unequal to any content, and two absences are equal. For every such path the engine compares three contents — the baseline payload (the version currently recorded for the name), the candidate payload (the requested new origin), and the content actually on disk — and tests one thing before anything else: if the disk already equals the candidate, including the case where both are absent, there is nothing to do, and the path classifies as `UNCHANGED`. This precedence is what makes an upgrade idempotent and re-runnable: a file the developer created with content byte-identical to what the candidate adds, a file the candidate removes that the developer already deleted, and every path a crashed run had already landed before it died all converge on `UNCHANGED` rather than being weighed against the baseline at all. Only for a path that does not already match the candidate do the remaining branches apply, relative to the baseline: present in the candidate, absent from the baseline, absent on disk classifies as `ADD`; the candidate differing from the baseline while the disk still equals the baseline classifies as `REPLACE`; present in the baseline, absent from the candidate, disk still equal to the baseline classifies as `REMOVE`; and the candidate equalling the baseline while the disk differs from both classifies as `KEEP_LOCAL` — the developer's own edit stands, including a deletion, and the engine writes nothing to that path. A path that reaches none of these — the candidate differs from the baseline, and the disk, independently, also differs from both the baseline and the candidate — is a doubly-changed file: it is not a sixth operation to perform, and it fails the whole upgrade with `CONTENT_CONFLICT`, naming every such target and path, rather than merging, splicing, or partially rewriting anything. A payload path where the disk holds a directory or a symlink instead of a regular file cannot be compared at all and refuses the same way, fail-closed, with `CONTENT_CONFLICT`. A file is written whole or not at all, and no hash set, digest index, or per-file record is persisted to make any of this comparison — it runs on the three contents' actual bytes, computed fresh at the moment the upgrade runs.

The baseline and candidate payloads a classification compares are both obtained by resolving an origin through the one shared resolver every other command already uses — the baseline by re-resolving the name's own currently recorded `origin`, the candidate by resolving the requested new one — so no snapshot of either is stored anywhere for this comparison, and neither ever comes from reading whatever the name's own inventory slot currently holds: a developer may have installed a different reference of the same identity into that slot since the name was last applied, and reading it directly would compare against content the registry no longer honestly names for this transition. A remote origin is recorded as the immutable value its fetch settled on, a commit SHA or an exact package version, so re-resolving it returns byte-identical content by construction (`cpt-frontx-adr-source-spec-syntax`); a `path:` origin carries no such pin, and it is usable as a baseline only because the recorded `version` is first confirmed to still match what that recorded origin currently reports — the same check `validate` performs against a stale local template — refusing with `VERSION_MISMATCH` and computing no plan when it does not hold, rather than classifying against a local folder the project's own record no longer honestly describes. This is why no baseline snapshot is captured into the local inventory and no per-file hashes are kept for this purpose: the minimal, algorithmic-baseline driver above requires the baseline to be derivable from data the project already keeps, and re-resolution of the recorded origin, guarded by that version check, is exactly that.

Resolving the candidate carries a further complication the baseline's own re-resolution does not: it names an identity the registry already occupies under this very name, so it cannot be read through the ordinary path a ready-to-adopt resolution would take, which would either overwrite the registered slot before the upgrade is even approved or refuse outright against the identity it is trying to read past. Every resolution serving an upgrade — the candidate's, the baseline's re-resolution above, and the re-resolution a failed commit's recovery performs below — therefore reads its content without ever adopting a new identity into the project or disturbing the registered slot, holding that content outside the slot until the transition's own commit promotes it.

Applying an approved plan follows a staged write, confined throughout to the paths the boundary above admits and never to a nested target belonging to another template: every `ADD` and `REPLACE` operation's new content is fully prepared before any destination path is touched, so a crash before that preparation completes leaves every target exactly as it was. Immediately before any destination is touched, the engine re-verifies that every destination the plan targets still holds exactly the content classification saw for it. No destination has been touched at this point, so there is nothing to undo if the check fails. If any destination has drifted since classification ran — a developer's edit landing in the interval between review and this moment — the engine refuses the whole upgrade with `CONTENT_CONFLICT` and writes nothing. This is a precondition on the plan the developer already approved, not a recomputation of it: it can only refuse, never change what was approved, so "reviewed equals applied" still holds even across that interval. Only past that check does the engine perform the destination writes themselves, atomically and confined to each target's effective ownership, while a `KEEP_LOCAL` or `UNCHANGED` path is never opened for writing at all. The residual limit is stated rather than implied: a write that lands after that check has already run is not detectable by this mechanism, and the repository's own version control is the remedy for it, the same as for any change a developer needs to inspect by hand.

The single atomic write of the project state document, recording the name's new `origin` and `version` together with the preceding pair reversal needs, is the transition's commit point: it lands only once every target's destination writes have landed, never earlier and never as a side effect of validation, so a crash or failure before it leaves the recorded entry exactly at the baseline it started from. Promoting the candidate's content into the name's local inventory slot is a second, separate write that follows the commit point rather than sharing its atomicity — two writes to two different stores are never one atomic write — precisely because a promotion failure must never be allowed to unwind a transition that has already committed: the slot's content is always re-derivable by resolving the now-current recorded origin, the same resolution every command needing that content already performs when it finds nothing staged, so a promotion failure costs availability of a shortcut, never correctness of the committed transition.

A failure the engine catches partway through the write phase is recovered, not merely retried: every destination it had already landed is returned to its baseline state — restorable because that baseline, like the candidate, is re-resolved rather than retained anywhere — and nothing is written to the project state document or the inventory slot unless every target's destination writes have landed cleanly. Caught before any destination has been touched, that recovery has nothing to undo and is trivially correct for exactly that reason. When the recovery itself cannot return every path to its baseline, the failure is reported together with every path recovery could not restore, so no partially-recovered target is ever reported as clean. Only a hard crash the process does not survive to catch escapes this recovery, and a half-written target can be exactly what it leaves behind; nothing here claims otherwise. What limits the damage then is ordering, not a rollback journal: because the project state write is last, the recorded entry still names the baseline regardless of how far a crash's write phase got, so re-running the identical upgrade converges on the intended state through the same disk-equals-candidate precedence that already makes the operation idempotent — every already-landed path needs no further write, and the run finishes whatever the crash never reached. That re-run, together with the repository's own version control for anything a developer needs to inspect by hand first, is the whole remedy; no separate crash-recovery procedure exists beyond it.

Reversal is carried by exactly one additional fact, and it is not content: a successful transition's commit also records, alongside the name's new `origin` and `version`, the one `{ origin, version }` the name held immediately before that transition — one generation, overwritten by whichever transition, upgrade or restore, runs next, never a longer history and never a per-file record. Restoring is the same engine invoked in the other direction, reached as `frontx upgrade <templateName> --restore` rather than a separate command: it treats the recorded preceding origin as the candidate and the currently recorded entry as the baseline, and runs the identical classification, review, and atomicity this decision fixes for the forward direction, including the same `CONTENT_CONFLICT` refusal for a doubly-changed file. A successful restore records the origin it just left as the new preceding origin, so a restore is itself reversible without any special case, and no content is ever stored for it because the preceding payload is re-resolvable from the preceding origin exactly as any other baseline is. `NOTHING_TO_RESTORE` means exactly one thing: no preceding `{ origin, version }` is recorded for the name at all — the name has never been upgraded or restored, or `register --replace` has since cleared the pair a prior transition left. A preceding origin that is recorded but cannot be resolved at all is `ORIGIN_UNAVAILABLE`, not `NOTHING_TO_RESTORE`; a preceding origin that resolves but no longer reports the version recorded beside it is `VERSION_MISMATCH` — the same baseline-honesty check the forward direction applies, now applied to the preceding pair, and the honest outcome for a `path:` origin whose folder has since moved on. No refusal is reachable by two codes. Reversing an upgrade whose preceding origin cannot be resolved this way remains available only through the repository's own version control, the same place the project's audit trail for this Git-tracked project state document already lives beyond the one generation this decision records — the same remote/local asymmetry `cpt-frontx-adr-source-spec-syntax` already fixes: a remote origin can be made reproducible and is, a local one cannot be, and this decision says so rather than fabricating a snapshot to paper over it.

The plan a developer reviews is exactly the plan that lands: it is computed once, presented once, and applied without recomputation, so nothing between approval and commit can change what was approved. A declined plan writes nothing — to any target, to the project state document, or to the registered name's inventory entry — leaving the repository exactly where it stood before the upgrade was attempted; whatever content the candidate's resolution had acquired is simply dropped, never promoted — and, since that content was never materialised anywhere, dropping it leaves nothing behind to clean up.

None of this introduces a new error code and none retires one: every refusal fixed above draws only from the shared, stable vocabulary `cpt-frontx-adr-cli-machine-readable-output` already fixes, which this decision does not amend.

This decision fixes the unit of operation (the template name, all its targets, atomically), the source of its baseline (the `project.json` registry entry, forward and preceding alike), the boundary a plan writes through and what it reports outside that boundary, the three-way whole-file classification that computes the plan, the staged write and the recovery that applies it, and the one-generation reversal that undoes it.

### Consequences

* Good, because the upgrade unit matches the registry structure exactly — one name, one origin, one version, several targets — so there is no field or state the registry can represent that upgrade cannot act on consistently.
* Good, because the baseline is data the project already carries for `list`, `validate`, and `apply` to auto-install a registered origin; upgrade introduces no dedicated baseline artifact, no file to go stale, and no record a developer could edit or delete out from under the upgrade — and reversal reuses that same data rather than a second store.
* Good, because atomicity across all targets of a name rules out a registry that claims one version while its targets sit at a mix of versions — a state a per-instance unit could produce and that a validator would otherwise need to detect and explain.
* Good, because the three-way whole-file classification never rewrites a file a developer has changed and never invents a merge inside it: a doubly-changed file stops the whole upgrade with `CONTENT_CONFLICT` instead of being silently overwritten or spliced.
* Good, because every resolution serving an upgrade — the candidate's, the baseline's, and recovery's — stages its content without touching or identity-checking the registered name's inventory slot, so classification can hold both the baseline and the candidate payload at once without any snapshot of either and without one resolution clobbering what another still needs.
* Good, because testing convergence first makes the operation idempotent and safely re-runnable: a developer's own byte-identical recreation of the candidate's content, a deletion that matches what the candidate removes, and every path a crashed run had already landed all resolve to `UNCHANGED` instead of a spurious `CONTENT_CONFLICT`.
* Good, because the plan a developer approves is the plan that lands, byte for byte, and a declined plan writes nothing to any target or to the project state document.
* Good, because reversal costs the project exactly one recorded `{ origin, version }` per name and no stored content, so the same minimal-baseline discipline that makes the forward move possible also makes the reverse move possible.
* Bad, because a developer cannot move one target of a multi-target template forward while leaving a sibling target behind (login on v2, registration still on v1); adopting a new version for any one target requires accepting it for all targets of that name, or not upgrading that name yet.
* Bad, because an upgrade that touches several targets at once must succeed or fail as a whole; a conflict or ownership violation confined to one target blocks the version change for every other target of the same name until that target's issue is resolved.
* Bad, because an upgrade is refused outright, with `CONTENT_CONFLICT`, whenever the same file has been changed by both the new template version and the developer (and disk does not already match the candidate); there is no partial credit for the files that would classify cleanly — the whole name's upgrade waits until the developer resolves the doubly-changed file(s) by hand.
* Bad, because ground put outside the boundary by any of those same terms — not only a newly declared exclusion, but a `projectOwnedRoots` entry, the local origin folder, `.frontx`, an environment-owned entry, or the separate nested-target exclusion — is left untouched and merely reported as `SKIPPED`, not cleaned up; a developer relying on an upgrade to fully modernize a target must separately notice and act on every skipped path.
* Bad, because ground the candidate's manifest newly claims can already be occupied by another template's nested target, refusing the whole upgrade with `TARGET_CONFLICT` — dropping an old exclusion can therefore block a name's upgrade on territory the developer did not expect to matter.
* Bad, because a restore does not unconditionally reproduce the pre-upgrade state: a file the forward upgrade added into ground it had newly claimed lies outside the preceding manifest's boundary from the restore's point of view, so restoring leaves it in place, reported `SKIPPED`, rather than removing it.
* Bad, because an edit landing in the interval between a developer's approval and the write phase's first rename can still cost a re-run: the verification pass immediately before that rename refuses the whole upgrade with `CONTENT_CONFLICT` rather than silently overwriting the edit, so the developer redoes review even though nothing was written; a write landing during the rename phase itself is narrower still and is not caught by anything here — only the repository's own version control reaches it.
* Bad, because a hard crash during the write phase runs no recovery at all and can leave a target genuinely half-written; the only remedy is re-running the identical upgrade, which converges through the same `UNCHANGED`-first precedence, or falling back to the repository's own version control for anything that needs inspecting by hand first.
* Bad, because a promotion failure after the commit point leaves the transition committed while the inventory slot still holds the prior content until some later resolution re-derives the now-current origin; the developer sees `INTERNAL` naming the stale slot, not a rolled-back upgrade.
* Good, because holding a resolution's content in memory rather than materializing it into a staging location leaves nothing for a killed process to orphan: this decision's requirement is only that such a resolution never adopt an identity or disturb the registered slot, and an in-memory handle satisfies that strictly. An earlier revision of this record accepted, as a cost, that an orphaned staging location could never be reclaimed automatically — since reclaiming it might delete a live invocation's still-needed payload — and would sit as inert residue inside the inventory store. That cost is not incurred: nothing consumes a staged copy, because promotion re-resolves the now-recorded origin rather than copying staged bytes. The mechanics are the shared resolver's own FEATURE to fix (`cpt-frontx-feature-template-resolution`), and it fixes them this way.
* Bad, because a `path:` origin's upgrade stops being reversible through the CLI once its folder has moved on from the version recorded beside the preceding origin: the CLI reports `ORIGIN_UNAVAILABLE` or `VERSION_MISMATCH` rather than restoring against content it no longer has an honest baseline for, and the developer is left to the repository's own Git history for that generation.
* Bad, because reversal reaches back exactly one generation: restoring after two upgrades in a row undoes only the most recent one, never the one before it, because the preceding `{ origin, version }` a commit records is overwritten by the next commit rather than accumulated into a history; calling `restore` a second time in a row does not reach back any further — it is a redo that returns to the origin the first restore left behind, and the generation before that stays unreachable.

### Confirmation

Compliance is confirmed by design and code review plus a CLI test: register a template applied to two targets under one name, then run `upgrade <name> <new-origin>`; assert the operation reads `{ origin, version }` from `project.json` (not any provenance or per-instance file) as its baseline, that both targets are validated and updated together, and that `project.json`'s `origin`/`version` for that name change exactly once, atomically, only on success. A companion test asserts that when validation fails for any one of the name's targets, `project.json` is left unchanged for every target of that name — no partial commit — and the result is reported as a single JSON envelope entry (e.g. `VERSION_MISMATCH`) rather than a per-target list of independent outcomes. A further test asserts that `upgrade` against a name with an empty `targets` list is rejected or redirected to `register --replace`, and that a plain `apply` re-run against an unchanged, already-applied target remains a no-op that performs no origin/version change.

A file-level test seeds a target with one file matching the baseline, one file changed only in the candidate, one file changed only on disk, and one file changed in both, then runs `upgrade`; it asserts the computed plan carries `ADD`/`REPLACE`/`REMOVE`/`KEEP_LOCAL`/`UNCHANGED` operations matching the three-way classification for the first three files, that the developer's on-disk edit to the `KEEP_LOCAL` file is untouched after the upgrade lands, and that the doubly-changed file causes the whole upgrade to refuse with `CONTENT_CONFLICT` naming that target and path, with nothing written anywhere. A convergence test seeds, separately, a file the developer created with content byte-identical to what the candidate adds, a file the candidate removes that the developer has already deleted, and a target left mid-upgrade by a simulated crash, and asserts every one of those paths classifies as `UNCHANGED` and re-running the upgrade to completion touches none of them. A companion test asserts that a payload path where the disk holds a directory or a symlink refuses the whole upgrade with `CONTENT_CONFLICT` fail-closed, that a symlink the developer created at a path neither payload declares is left untouched and causes no refusal, and that a materialized `ADD` creates whatever parent directories it needs while a `REMOVE` leaves the directory it empties in place. A further test seeds a temporary file matching the write phase's reserved naming convention inside the boundary before an upgrade runs, and asserts classification excludes it from every comparison and the next upgrade of that name reclaims it rather than reporting it as a developer's own file. A further test registers a template whose own payload declares a path matching that reserved convention and asserts pre-publish validation refuses a published template outright; a companion test does the same for a local `path:` template, which has no publication step for that check to run against, and asserts the colliding path instead reaches a plan reporting it as `SKIPPED`, naming the collision, never silently dropped.

A boundary test registers a name whose baseline manifest excludes a subtree the candidate manifest now excludes as well plus one more, and asserts the plan reports every path under the newly-excluded subtree as `SKIPPED`, writes none of them, and computes the boundary once from the candidate manifest rather than per path. A companion test separately seeds a payload path inside a `projectOwnedRoots` entry, the local origin folder, `.frontx`, and an environment-owned entry, and asserts each is reported `SKIPPED` by the same plan regardless of which term it falls under. A further test has the candidate manifest drop an exclusion the baseline held over ground now occupied by a developer's own edited file, and separately by another template's nested target, and asserts the first refuses with `CONTENT_CONFLICT` and the second with `TARGET_CONFLICT`, both existing codes. A restore of that same upgrade is asserted to compute its boundary from the preceding manifest rather than the manifest the forward upgrade used, to reproduce the preceding content for every target within that boundary, and to leave in place — reported `SKIPPED`, not removed — any file the forward upgrade had added into ground it newly claimed.

A staged-write test asserts that a crash before any destination is touched leaves every target byte-for-byte as it was, that a precondition check immediately before any destination is written refuses the whole upgrade with `CONTENT_CONFLICT` when a destination has drifted since classification, and that the project state document is written only after every target's destination writes have landed; the write-phase mechanics that deliver these properties are the owning FEATURE's own concern. A companion test asserts that a caught I/O failure during the write phase is recovered rather than merely retried, leaving `project.json` and the inventory slot untouched and returning `INTERNAL`, and that a recovery which cannot return every path to baseline still leaves the project state store and inventory untouched. A further test simulates a hard crash with no recovery run at all, asserts a target can be left genuinely half-written while `project.json` still names the baseline, and that re-running the identical upgrade converges on the intended state. A further test forces the post-commit promotion step, and separately the post-commit AI-bundle refresh, to fail, and asserts each leaves the committed transition standing and reports `INTERNAL` naming what it could not refresh.

A reversal test runs an upgrade to completion, asserts the committed entry carries the one preceding `{ origin, version }` alongside its new `origin`/`version`, invokes `upgrade <name> --restore` and asserts it reproduces the pre-upgrade content within the preceding manifest's boundary and records the just-left origin as the new preceding origin, then invokes `restore` a second time in a row and asserts it is a redo that moves the name back to the origin the first restore had left behind, never a further rewind to the generation before the original upgrade, which stays unreachable. A further test asserts `restore` returns `NOTHING_TO_RESTORE` for a name with no preceding pair recorded, `ORIGIN_UNAVAILABLE` for a name whose recorded preceding origin cannot be resolved at all, and `VERSION_MISMATCH` for a name whose recorded preceding origin resolves but no longer reports the version recorded beside it — three distinct codes for three distinct conditions, none of them interchangeable. A further test resolves a candidate origin during an upgrade that is then refused during validation or declined at review, and asserts in both cases that the registered name's inventory slot is untouched and the candidate's resolution is discarded rather than promoted; that resolution's own mechanics — that it materializes nothing, so there is no address to collide on and no residue for a killed process to leave behind — are confirmed by the shared resolver's own FEATURE.

## Pros and Cons of the Options

### Per-applied-template-instance upgrade with a provenance-derived baseline and file-level reconstruction

One engine invocation per applied instance, reading a dedicated per-instance provenance record as the diff baseline and reconstructing a three-way merge from it.

* Good, because each instance upgrades fully independently of every other instance of the same template.
* Bad, because it requires a per-instance provenance record and file-level baseline reconstruction that the project-state contract does not carry, so choosing it here would mean adding contract surface for a capability v1 does not need.
* Bad, because it has no baseline to read under the new `project.json`-only registry: there is no per-instance record left to diff against.

### Per-target upgrade with independently versioned instances of the same template

Keep the instance as the unit, but let each target of a given template name carry its own `origin`/`version`, so different targets of the same name can sit at different versions.

* Good, because it preserves the flexibility of upgrading targets one at a time.
* Bad, because it breaks the registry's own invariant — one `origin` and one `version` per template name — forcing `templates[name]` to become a map of per-target versions and reopening a structural question the project-state contract settles elsewhere (`cpt-frontx-adr-project-provenance-record`).
* Bad, because it complicates every other registry-reading operation (`list`, `validate`, auto-install on `apply`) with a per-target version dimension none of them currently need.

### Atomic all-targets upgrade with a `project.json`-read baseline, whole-file classification, and one-generation reversal

The template name is the unit; `upgrade` validates and moves every target under that name together, atomically, using the name's own registry entry as the baseline, moving content onto each target through a three-way whole-file classification against that baseline, and reversing an applied upgrade by re-running the same classification against the one preceding `{ origin, version }` its commit recorded.

* Good, because it requires no new persisted state — the baseline is the registry entry every other command already reads and writes.
* Good, because a registry entry can never describe a template name at an internally inconsistent version across its own targets.
* Good, because three-way whole-file classification against a re-resolved baseline needs no additional stored artifact — the same registry entry read for the unit-and-baseline choice also carries what the classification and the reversal need.
* Good, because refusing a doubly-changed file outright, rather than merging or overwriting it, keeps every write inside a target's effective ownership either a clean whole-file operation or no operation at all.
* Neutral, because it provides useful, if coarse, determinism for v1 while leaving room for a future decision to introduce finer-grained reconciliation if a validated need for it appears.
* Bad, because it cannot express "upgrade this one target, leave the others" — a real workflow a per-instance unit would support and that a future decision may need to introduce deliberately.
* Bad, because a `path:` origin's reversibility is only as good as the honesty check on its recorded version — once that check fails, the CLI itself offers no restore, only the repository's Git history.

### Textual three-way merge with conflict markers in the file

Merge the baseline, the candidate, and the on-disk content line by line, writing conflict markers into a target file wherever automatic resolution is not possible, in the pattern conventional version-control merges use.

* Good, because a file with a resolvable divergence is upgraded automatically, without stopping the whole name's upgrade to ask the developer to choose.
* Bad, because it writes into a file the developer may be actively editing, which is exactly the destruction the non-destructive driver forbids, whether or not the write later requires manual conflict resolution.
* Bad, because the unit a developer reviews becomes a hunk buried inside a file rather than a whole file named in a plan, so approval happens after the fact, on a file already rewritten, rather than before any write.
* Bad, because it reintroduces the region-marker merge machinery this ecosystem has separately decided to drop, for a benefit — automatic line-level resolution — none of this decision's drivers ask for.

### Whole-target re-materialisation from the new payload

Skip classification and overwrite every file the new template version declares within a target's effective ownership, whether or not the developer has touched it.

* Good, because atomicity is trivial to satisfy: the target ends up byte-for-byte at the new version with no partial state possible.
* Bad, because it destroys every in-progress edit inside the ownership boundary, which the non-destructive driver forbids outright and which whole-file classification exists specifically to avoid.
* Bad, because it gives a developer nothing to review beforehand beyond "this target will be replaced," rather than the specific set of adds, replacements, and removals the classification computes.

### A retained pre-upgrade content snapshot under `.frontx/` as the restore carrier

Capture a copy of every target's pre-upgrade content into the repository at the moment an upgrade commits, and read that copy back for both the forward diff's baseline and a later restore.

* Good, because a restore never depends on any origin still being resolvable — the content is already sitting in the repository.
* Neutral, because the pattern has prior art in template tools that keep an answers/context snapshot beside applied output for the same reason (Copier's `.copier-answers.yml`, `cruft`'s equivalent link file) — precedent for the shape of a solution, but not one this decision needs once re-resolution serves the same purpose without a second file.
* Bad, because it duplicates, inside a Git-tracked repository, content that repository's own history already holds.
* Bad, because it adds a second CLI-written state artifact alongside the project state document, with its own retention, staleness, and deleted-out-from-under-the-engine questions the single-document driver exists to avoid.
* Bad, because it is unnecessary once the preceding origin alone makes the preceding payload re-resolvable: the minimal-baseline driver excludes a baseline kept solely to serve upgrade.

### A per-file content-hash index maintained for upgrade

Maintain a persisted hash for every file inside an applied target's ownership, updated on every apply and upgrade, and use it to detect which files have changed instead of comparing content directly.

* Good, because comparing hashes avoids reading full file content for files that have not changed.
* Bad, because the record's own minimal-baseline driver excludes a baseline kept solely to serve upgrade, and a per-file hash index is exactly that: state that exists for no reason but this comparison.
* Bad, because classification needs no index — the three contents it compares are all obtainable at the moment the upgrade runs, so an index only adds a second thing that can drift from the files it describes.

## More Information

The reviewable, non-destructive, reversible discipline this decision's drivers require is delivered by the mechanism above, not carried forward as an unmet placeholder: the plan a developer reviews is the plan that lands, a verification pass immediately before any destination is written catches a file the developer has changed since review so no write past that pass destroys it, and every applied upgrade remains reversible for one generation through the same engine run in the other direction — short of a write landing after that pass itself, which nothing here detects and which the repository's own version control remedies. `cpt-frontx-fr-cli-project-upgrade-changeset`, `cpt-frontx-fr-cli-upgrade-review-approval`, and `cpt-frontx-fr-cli-upgrade-restore` are therefore requirements this decision's mechanism actually carries out, not requirements waiting on a mechanism still to come.

A template registered from a local `path:` origin has no separate publication to pin against, so this decision's baseline for such a name is only as trustworthy as the recorded `version` still being what that origin currently reports: the classification refuses the whole upgrade with `VERSION_MISMATCH`, computing no plan, whenever a `path:` origin's folder has drifted from the version recorded beside it, rather than classifying against a local folder the project's own record no longer honestly describes. A remote origin never faces this refusal for drift, because its pinned commit or package version is immutable and re-resolves byte-identical by construction; the refusal exists only for the one origin kind that can actually move out from under the record, and it is the resolution this decision reaches, not a constraint it leaves open.

The exact field layout `project.json` uses to record `{ origin, version, targets }`, the one preceding `{ origin, version }` a successful transition also records for reversal, and the field layout of the plan itself — the shape class fixed above, not its concrete JSON — are none of them fixed here; per `cpt-frontx-adr-contract-schema-ownership`, each layout belongs to the owning FEATURE, and this decision relies only on an `origin`/`version` baseline and one preceding `origin`/`version` being readable per template name, and on the plan expressing the shape class fixed above, however each is laid out. The behavior this decision constrains is delivered by the CLI's change-set-and-upgrade component, `cpt-frontx-component-cli-change-set-engine`, established as one of the CLI's internal components in `cpt-frontx-adr-cli-internal-decomposition`.

The engine this decision fixes operates independently of any AI layer: `frontx upgrade <templateName> <new-origin>` is a direct CLI invocation that validates and moves a template name's targets whether a developer types it themselves or an AI orchestrator issues it on their behalf, reaffirming the orchestration boundary `cpt-frontx-adr-ai-driven-upgrade-orchestration` already fixed — the CLI executes and arbitrates the single engine this decision fixes, and an AI layer only sequences and interprets around it. A successful upgrade also refreshes the applying name's CLI-owned AI bundle — `.frontx/ai/<manifest-name>/`, materialized as described in `cpt-frontx-adr-template-ownership-boundary-declaration` — from the new version's payload, the same way `apply` refreshes it on first materialization; a successful restore refreshes the same bundle from the preceding version's payload, since restore is the same engine run in the other direction. A failure refreshing that bundle leaves the transition itself standing, exactly as a promotion failure does, because the bundle is equally re-derivable from the now-current payload whenever something next refreshes it.

Integration analysis (**INT**): the upgrade operation is an internal CLI contract with no external party — its producer is the `upgrade` command and its consumer is the local project (`project.json` plus the files under each target). Version-compatibility intent is forward-looking only in the sense that the JSON result envelope's error vocabulary (including `VERSION_MISMATCH`) must remain stable for scripted and AI-driven callers; the internal baseline representation is free to evolve as `project.json`'s owning FEATURE evolves it.

Applicability of the remaining checklist categories:

* **PERF** — Not applicable, because comparing three whole-file contents for a bounded, developer-sized list of targets under one template name carries no throughput or latency budget at decision altitude.
* **SEC** — Not applicable, because the operation handles template origins, version strings, and file content the developer already has locally, not secret material.
* **REL** — addressed, with an explicit limit stated rather than implied: the all-or-nothing atomicity requirement is one reliability property this decision fixes (no partial commit across a name's targets on failure), and the staged write is the second — a crash before any destination is touched leaves every target byte-for-byte as it was, and a failure caught while writing is recovered rather than merely retried, because the baseline it restores to is always re-derivable rather than retained. A hard crash the process does not survive to catch runs no such recovery and can leave a target genuinely half-written; because the project state write is last, the recorded entry still names the baseline regardless, so re-running the identical upgrade converges on the intended state, and that re-run plus the repository's own version control is the whole remedy for what recovery itself cannot reach. A precondition check immediately before any destination is written closes the review-to-commit window except for a write landing after that check itself, which nothing here detects. A promotion failure after the commit point never unwinds the transition already committed, since the inventory slot's content is re-derivable by resolving the recorded origin whenever something next needs it. Reversal is bounded reliability, not unlimited: one generation, restorable through the same engine, and refused only when no preceding generation is recorded at all — never when a recorded preceding origin merely cannot be resolved or no longer matches what it once reported, which are reported as the distinct conditions they are.
* **DATA** — Not applicable as a complete schema, because the `project.json` field layout, including the one preceding `origin`/`version` this decision requires alongside it, and the plan's own data payload field layout, are each owned by their FEATURE per `cpt-frontx-adr-contract-schema-ownership` and, for the envelope's `data` payload specifically, the scoping `cpt-frontx-adr-cli-machine-readable-output` already fixes; this decision fixes only that an `origin`/`version` baseline and one preceding `origin`/`version` are read and recorded per template name, and that the plan expresses the shape class this decision names.
* **OPS** — Not applicable, because no operational procedure attaches to a local developer command.
* **MAINT** — addressed: one baseline source, one classification mechanism, and one engine run in either direction for upgrade and restore remove the bookkeeping a per-instance provenance store, a snapshot artifact, or a hash index would otherwise require.
* **UX** — addressed implicitly: a developer reasons about upgrading or restoring a template by name and reviews one plan of whole-file operations, not about reconciling divergent versions across its individual targets or resolving a merge conflict inside a file.
* **BIZ** — Not applicable, because product requirements live in the PRD and are cited here by ID.
* **COMPL** — Not applicable, because an upgrade moves a developer's own files inside their own checkout under explicit approval; no regulated data is processed, and nothing must be retained beyond the one generation the project state document already keeps.

**Review cadence**: revisit if a validated need emerges for upgrading one target of a multi-target template independently of its siblings, or for reversing an upgrade more than one generation back.
