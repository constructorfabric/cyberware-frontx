**ID**: `cpt-frontx-adr-ai-driven-upgrade-orchestration`
## Context and Problem Statement

A Project Developer must be able to use AI agents to orchestrate a template upgrade — analysing the change between template versions, applying the upgrade, and validating downstream effects — through an AI-driven workflow that includes review gates, change analysis, and downstream-impact assessment (`cpt-frontx-fr-ai-upgrade-orchestration`, `cpt-frontx-usecase-ai-driven-template-upgrade`). A single change-set engine already owns the production of a reviewable, approvable, non-destructive upgrade change set in the CLI (`cpt-frontx-adr-project-upgrade-mechanism`). How should the AI orchestration relate to that engine — as a coordinating layer above it, or as a second, independent mechanism?

## Decision Drivers

* **One source of truth for the change set** — the bytes applied to a project on upgrade must be produced by one engine, so that an AI-driven upgrade and a direct CLI upgrade yield the same reviewable change set (`cpt-frontx-fr-ai-upgrade-orchestration`).
* **Alongside, not subordinate** — the AI workflow runs alongside direct CLI invocation as a guided path, not as a replacement for or a dependent of the CLI's command surface (`cpt-frontx-usecase-ai-driven-template-upgrade`).
* **Review-gate integrity** — developer review and approval must gate the upgrade before any project file is written; the orchestration adds gates and analysis on top of an engine whose apply step is already non-destructive (`cpt-frontx-fr-cli-upgrade-review-approval`).
* **Recoverable, non-destructive apply** — a version transition must be reversible and must never leave a project half-written, a property already guaranteed by the single change-set engine and inherited rather than reimplemented.
* **AI value-add** — the orchestration must contribute change analysis and downstream-impact assessment that enrich the engine's raw change set, not duplicate the engine's mechanics.

## Considered Options

* **Single CLI engine, AI orchestrates and enriches it** — there is exactly one template-version change-set engine, owned by the CLI (`cpt-frontx-adr-project-upgrade-mechanism`). The AI workflow surface invokes that engine to produce the change set, then enriches the flow with change analysis, review gates, and downstream-impact assessment. It operates alongside the CLI, not subordinate to it, and implements no second engine.
* **Two independent engines** — the AI Tooling Framework implements its own change-set engine for AI-driven upgrades, separate from the CLI's engine, each producing its own change set.
* **AI as a thin pass-through** — the AI workflow merely forwards the developer's intent to the CLI engine and relays its output verbatim, adding no analysis, gates, or downstream-impact assessment of its own.

## Decision Outcome

Chosen option: **Single CLI engine, AI orchestrates and enriches it**, because it is the only option that keeps one source of truth for the applied change set while still delivering the guided, analysis-rich workflow the use case calls for. There is a single template-version change-set engine, and it lives in the CLI (owned by `cpt-frontx-adr-project-upgrade-mechanism`). The AI orchestration layer **invokes** that one engine to produce the reviewable change set and **enriches** the flow around it — change analysis of the version transition, review gates before apply, and downstream-impact assessment — surfacing incompatibilities for the developer to act on before the change set is applied. The orchestration operates **alongside, not subordinate to** the CLI: a developer may upgrade directly through the CLI or through the AI-guided flow, and both apply the identical change set produced by the same engine. The AI layer does **not** implement a second change-set engine.

This relationship governs **every CLI engine the framework drives**, not the change-set engine alone; the upgrade flow is the case it was decided on, and the scaffolding flow takes the same shape. There, the framework chooses which installed templates answer a developer's stated intent - matching that intent against the description each template's manifest declares (`cpt-frontx-adr-template-manifest-contract`) - and then **invokes** the CLI's assembler to apply them, seeding the repository with one template and adding each further distinct template. It materializes no file itself and reproduces no part of resolution, assembly, conflict checking, or provenance writing, exactly as it implements no second change-set engine; and it runs alongside the direct path, so a developer who already holds a template reference reaches the identical result by invoking the commands directly. What the framework adds on this path is the selection and the plan, not a second way to write a project.

The scope of this decision is the relationship between the AI orchestration surface and the CLI engines it drives - which side owns engine mechanics (the CLI) and which side owns the guided workflow (the AI Tooling Framework). It does not redefine any engine's internals, the change-set format (those belong to `cpt-frontx-adr-project-upgrade-mechanism`), or the assembly mechanism (`cpt-frontx-adr-uniform-template-mechanism`). The two-engines option produces divergent change sets for the same upgrade and doubles the surface that must remain non-destructive and recoverable; the thin-pass-through option keeps a single engine but abandons the analysis, gating, and downstream-impact assessment the use case requires, leaving the AI flow with no value over a bare CLI call.

### Consequences

* Good, because exactly one engine produces the applied change set, so an AI-driven upgrade and a direct CLI upgrade are byte-for-byte equivalent and equally reviewable.
* Good, because the AI flow adds change analysis, review gates, and downstream-impact assessment without duplicating engine mechanics.
* Good, because the engine's non-destructive, recoverable apply and its rollback behaviour are inherited unchanged; the orchestration adds no new way to half-write a project.
* Neutral, because the orchestration depends on the CLI engine's invocation surface remaining stable across versions, which the matched-version policy already governs.
* Bad, because a defect or limitation in the single engine affects both the direct and the AI-guided path; there is no independent second implementation to fall back on.
* Bad, because the orchestration's enrichment is only as good as the engine's change-set fidelity — the AI layer cannot surface a downstream impact the change set does not expose.
* Good, because one relationship covers every engine the framework drives, so the scaffolding path inherits the assembler's pre-flight conflict check and per-template provenance rather than acquiring a second way to write a project.
* The framework's writes are **excluded** wholesale: on either path it holds no code path that materializes or modifies a project file, so every write a developer sees is one a CLI engine performed and recorded. The exclusion binds the framework's code, not every byte written while an agent follows a framework document: inside ground an applied template already owns, an agent following that template's own shipped conventions exercises the **template's** delegated authority, with the framework contributing the sequencing and the intent-stated content and none of the structure, naming, identifiers, or registration. Applying a template is still the CLI's alone, and no template is applied twice.
* On the scaffolding path the framework **excludes** re-applying a template to a target that template already occupies, because the assembler it drives treats that as an idempotent no-op decided purely by whether the target is already recorded under the template's name in `.frontx/project.json` — never by re-reading or reconciling disk content (`cpt-frontx-adr-composed-template-resolution`); any other overlap is refused pre-flight (`cpt-frontx-adr-assembly-conflict-prevention`). Repetition within an applied template's own ground is left to the extension skills that template activates (`cpt-frontx-adr-extension-discovery-activation`).

### Confirmation

Confirmed by review and by an integration check that the AI-guided upgrade and the equivalent direct CLI upgrade, run against the same project and the same target template version, produce the identical change set - demonstrating a single engine rather than two. A code review confirms the AI Tooling Framework contains no second change-set engine implementation and reaches the engine only through the CLI's invocation surface, and that a review gate stands before any project file is written. The same review confirms the scaffolding path drives the assembler through that invocation surface and through no other route - no linked engine, and no read of the CLI's own storage - and that the framework holds no code path that materializes or modifies a project file on either path.

## Pros and Cons of the Options

### Single CLI engine, AI orchestrates and enriches it

One engine in the CLI produces the change set; the AI layer invokes it and enriches the flow with analysis, gates, and downstream-impact assessment, operating alongside the CLI.

* Good, because there is one source of truth for the applied change set across both upgrade paths.
* Good, because review gates and analysis are added without reimplementing engine mechanics.
* Good, because the engine's non-destructive apply and rollback are inherited intact.
* Neutral, because it couples the orchestration to the engine's invocation surface, which the version policy already stabilizes.
* Bad, because both paths share the single engine's limitations.

### Two independent engines

The AI Tooling Framework implements its own change-set engine, separate from the CLI's.

* Good, because the AI path could evolve its engine independently of the CLI's release cadence.
* Bad, because the same upgrade can yield two divergent change sets, undermining a single reviewable result.
* Bad, because the non-destructive, recoverable apply guarantee must now be built and maintained twice.
* Bad, because two engines double the surface a developer must trust and a reviewer must reason about.

### AI as a thin pass-through

The AI workflow forwards intent to the single CLI engine and relays its output verbatim, adding nothing.

* Good, because it preserves a single engine with minimal new surface.
* Bad, because it delivers no change analysis, no review gating, and no downstream-impact assessment, so it fails the use case.
* Bad, because it gives the AI-guided path no value over a direct CLI call, defeating the reason to offer it.

## More Information

The single engine this orchestration coordinates with is decided in `cpt-frontx-adr-project-upgrade-mechanism` (the CLI's change-set engine); the orchestration is delivered by the AI Tooling Framework component `cpt-frontx-component-ai-tooling-kit` and the engine by `cpt-frontx-component-cli`. These pointers identify related decisions and components and are not part of this decision's durable identity.

Integration treatment (INT): the framework integrates with the CLI across one surface — the command/invocation surface — and with more than one engine behind it: the change-set engine on the upgrade path, and on the scaffolding path the template resolver's machine-readable listing and the assembler's seed and add commands. **Integration impact (INT-ADR-001)** — the framework consumes that command surface and the outputs it returns (the change set, the listing's records, each apply command's reported outcome); their version compatibility is anchored to the ecosystem's matched-version policy rather than negotiated ad hoc, so a framework release pairs with a compatible CLI release. **Contract changes (INT-ADR-002)** — a change to any consumed command's invocation shape or output shape is a contract change the framework must absorb, whether it lands in the change set, the listing envelope, or an apply command's arguments; backward-compatible additions leave the framework working unchanged, while an incompatible change is governed by the version bump that pairs the two. The version-transition path for the orchestration itself is therefore the matched-version policy, not a separate negotiation.

Reliability treatment (REL): **Reliability impact (REL-ADR-001)** — the framework adds no new failure mode to any apply step, because no code path it ships writes a project file: every write an engine performs is one that engine recorded, and a failure during selection, analysis, or gating leaves the project untouched because nothing has been written by then. The one write that does not come from an engine is the delegated one — content created inside ground an applied template already owns, by an agent following that template's own shipped conventions (see the exclusion bullet above). It is the template's authority rather than the framework's, it happens only after the CLI has applied that template and recorded it, and it is bounded by the ground that template declared; so it adds no writer to the framework and leaves the pre-apply guarantee intact. The single engine is a shared dependency of both upgrade paths — a single point of failure for upgrades by design — and the trade-off is accepted in exchange for one source of truth for the change set. **Operational readiness (REL-ADR-002)** — recovery from a declined or failed upgrade is the engine's existing behaviour: no change set is applied, so the project remains at its current version with no files written; the orchestration's review gate is the point at which a developer can decline before any apply, and the downstream-impact assessment is surfaced before the gate so incompatibilities are visible at decision time.
